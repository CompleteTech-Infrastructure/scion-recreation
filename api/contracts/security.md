# Security and permission-safe object delivery (`security-v1`)

Status: proposed product contract for review. It specifies original design choices for this recreation; it does not describe unpublished Anthropic internals, implementation behavior, or an accepted security promise. Wire encoding and canonical path transport representation remain subject to the shared FND-03 freeze. FND-04 must consume these projection semantics before its wire contract is frozen.

## Principal and policy identity

1. Every request is evaluated for one authenticated principal and one authenticated session. A principal is an issuer-scoped, opaque subject identity with a class: `human`, `build_job`, `model_worker`, or `service_account`. Node daemons and regional caches authenticate as serving workloads and never substitute for the requesting principal.
2. A credential resolver verifies issuer, signature, subject, class, audience, validity interval, and revocation state before authorization. Caller-supplied actor names, author fields, repository IDs, local user names, or object digests do not establish identity. Authentication uncertainty fails closed.
3. A delegated job or worker has its own principal/session identity and an explicit delegation from its initiating actor. It does not inherit the initiator's broader rights implicitly. Each request and grant is bound to both principal and session; another session cannot replay it.
4. Policy is versioned and auditable. Each successful authorization decision names the repository policy version and effective security view used. Policy version changes invalidate derived decisions, grants and projections according to the freshness rule below. Audit records identify the principal, action, resource class, result and policy version, but omit credentials and hidden path bytes.
5. An article, repository file, model prompt, imported instruction, or other source-controlled content is untrusted data. It cannot create a principal, grant, role, policy rule, delegation, or exception to this contract.

`effective_view_id` is an opaque authority-issued identity for the authenticated principal/session's effective path and metadata rights at a source revision under one immutable policy version. It distinguishes different readable scopes even when source revision is identical. It is principal/session scoped, rotates when relevant policy or rights change, and carries no rights itself. Cross-principal reuse of projected bytes is allowed only when separately authorized for the receiving principal; object grants remain principal/session bound.

## Default-deny authorization and byte paths

1. The default is deny at both repository and path scope. A request requires active repository membership and the repository-level capability for that action, plus all required path actions; a path right cannot create membership or a repository capability, and membership alone grants no path read. Capabilities for read, write, metadata-read, history-read, search, review, approve, land, administer-policy, and operate-infrastructure are distinct. No role implies approval, policy administration, or infrastructure operation unless an explicit versioned role definition grants that capability.
2. Policy rules grant or deny one or more of `traverse`, `list`, `read`, and `write` at a repository root or directory prefix. Evaluate every applicable repository rule and every matching prefix. Any explicit deny for the requested action at either scope wins over every matching allow, including a deeper allow. Missing rule, expired grant, unresolved group, or policy lookup failure is deny. Policy edits are versioned and auditable; a writer cannot grant itself administration or approval.
3. Repository paths are sequences of raw bytes. Byte `2f` (`/`) alone separates components. Do not decode UTF-8, case-fold, Unicode-normalize, percent-decode, translate backslash, or otherwise normalize before policy comparison. Non-UTF-8 names remain distinct and must be represented losslessly at the API boundary; display escaping is presentation only.
4. A non-root directory prefix is a valid slash-separated relative path with no trailing slash. It matches path `X` iff `X == P` or `X` begins with `P || 2f`. Thus bytes `61` (`a`) match `61` and `61 2f ...`, but not `61 62` (`ab`). Prefix tests compare raw bytes. The root rule uses an explicit `ROOT` selector distinct from an empty byte string; empty bytes are never silently treated as a path or root prefix. Path syntax and canonical request encoding follow FND-03; this contract requires that encoding to preserve exact bytes.
5. To reach a path, the principal needs `traverse` on every ancestor directory. Enumerating immediate child names requires `list` on that directory. Returning file bytes requires `read` on the file path. A mutation requires `write` on the affected path and the necessary ancestor traversal; rename/move checks source removal and destination creation independently, and both must pass before any visible result or mutation. Directory listing does not grant reads of child content; read permission does not grant directory listing.
6. A denied ancestor is hidden: no descendant lookup may return its name, that a child exists, its child count, or a distinguishable hidden/missing result. A caller who already knows a path still needs traversal and the requested action. Rename, diff, blame, merge, history, and conflict evaluation apply these rules to each input and output path; a revision or branch alias never bypasses current policy.

## Object grants and raw-object boundary

An object digest is an identifier and integrity check, never a bearer capability. Authority issues an opaque, authenticated `ObjectGrant` with at least these semantic claims:

```text
version = security-v1
principal_id, session_id
repository_id
scope = exact (object_kind, object_id) OR exact projection_id
right = read
policy_version, effective_view_id
audience = one serving tier/service
issued_at, expires_at
authorization_proof = authority-verifiable, bounded reachability or full-object-read proof
```

The binary/token encoding is not frozen here. A grant is accepted only for its exact principal, session, repository, scope, right, audience and valid time interval. It cannot be widened, forwarded to another tier, converted from a projected view to a raw object, or renewed from a cache hit. A grant to one object or view says nothing about any other digest.

For every blob delivery, the authority must establish a bounded proof that the exact blob is reachable at a path the principal may read in the named repository revision and effective view. A visible projected-manifest entry may supply an opaque descendant proof. The proof binds the repository, revision, exact path bytes or visible entry identity, target blob, view, policy version, and read right. A grant is scoped to the exact blob, but the scope alone is insufficient: there is no pathless blob grant. An arbitrary blob digest, a raw tree grant, or a digest shared with another repository is not reachability proof. For raw trees and changesets, the authorization proof instead establishes the full-object-read decision over their complete visible contents and required history identity.

Raw blobs may be returned only under a valid exact-object grant backed by authorized reachability. Full-object-read requires active repository read plus `traverse`/`list` rights for every represented directory, `read` for every represented file/blob reference, and explicit `metadata-read`/`history-read` rights for every metadata field or history edge present. A raw tree or raw changeset is allowed only when this complete decision passes and every name, path operation, child/object identity, and metadata field carried by that raw object is visible under current policy. If any part is hidden, raw bytes are denied and the caller must use an authorized projection. This includes `GetChangeset`: its canonical raw payload contains all `changed_paths` and referenced blob IDs, so a generic repository `read` permission alone is insufficient for the raw response.

Grants authorize each response, not just request initiation. Check them before every object delivery, cache hit, miss, range, resumed stream, retry, snapshot-derived fetch, or local-daemon response. Range grants also bind the exact object, byte range/maximum bytes, stream/session, audience, and expiry; a continuation cannot change object, principal, repository, or view. A cache must not fetch upstream or reveal whether an object is present until authorization succeeds. Denial responses for hidden and nonexistent resources use a consistent non-enumerating public shape; internal audit may retain the reason without hidden names.

## Authorized manifests and projected changesets

1. For a partially authorized directory, the authority returns an `AuthorizedManifest` containing only visible entries. Its opaque projection identity is a distinct authority-issued `projection_id` semantically bound to `(repository_id, source_revision, effective_view_id, policy_version, exact_selection, projection_algorithm_version, projected_entries)`. The selection is either explicit `ROOT` or exact raw path bytes. This binding does not require exposing a hidden source revision or tree ID; disclose those only if separately authorized. The identity is not a source tree digest and is not authorization by itself; reads of the manifest and children still require a current grant.
2. A projected manifest exposes only entries the principal may list and traverse. It contains no hidden-name placeholders, hidden child IDs, omitted-entry counts, raw-tree IDs, raw chunk/page boundaries, hidden-name-bearing cursors, or error text derived from hidden entries. Visible entries are ordered by unsigned raw-byte path order for stable pagination. Child projection IDs are view-scoped. A cursor binds the projection ID, policy version, selection, page size and position within the projected result.
3. If a principal cannot read a complete raw changeset, the authority returns a separate `ProjectedChangeset`, never the original canonical payload. It filters each changed-path operation under the same current traversal/read rules; a `SET` exposes its target blob ID only when the path proof authorizes that exact blob. The projection includes only separately authorized metadata and history fields. Hidden parent identities and hidden operations are omitted; the projected response must not preserve a hidden operation count or signal hidden fields with placeholders. Parent links are emitted only when their identities are visible under current history policy.
4. The opaque projected-changeset identity is distinct from the source changeset ID and is semantically bound internally to `(repository_id, source_changeset_id, effective_view_id, policy_version, exact_selection, projection_algorithm_version, projected_payload)`. This internal binding does not require disclosing a hidden source changeset ID. The projection ID is an identity for this read model only. It must never be presented as the original changeset hash, native canonical bytes, signed payload, or proof that a source signature authenticates the projection. Any projection digest is integrity metadata, not an access grant.
5. Projection identity must change when any bound view, policy version, source revision, selection, or algorithm version changes, even if the visible bytes happen to be identical. It must distinguish different effective views over the same source revision. Reuse of a prior-policy projection as a current authorization result is forbidden.
6. Raw trees/changesets require full-object-read authorization as defined above. There is no client flag, cache mode, snapshot mode, history endpoint, or “debug” endpoint that bypasses projection. An authority failure while generating a projection fails closed; it does not fall back to raw content.

The exact projection encoding and shared byte-path parser are coordinated with FND-03/FND-04. Until those contracts freeze, `projection_id` is an opaque semantic tuple, not a new canonical object format.

## Cache, history, search and snapshot isolation

1. Serving tiers use one authorization contract at authority, regional and node tiers. Cache keys for projected data include the full projection identity. Immutable object bytes may be physically deduplicated across users or repositories, but permission decisions and grants are never shared on digest equality.
2. On a denied or unproven request, do not probe a content cache, disk path, snapshot index, or upstream tier. This prevents a hot/cold cache distinction from becoming an existence oracle. For an allowed request, verify the exact grant and current-policy freshness before bytes are emitted, including on cache hits. A corrupt/missing cache object is an explicit failure, never a reason to skip authorization or flood another tier.
3. Snapshots are integrity-checked, versioned and scoped to an audience and declared projection/view. Snapshot possession, manifest IDs and a snapshot's old grants confer no current right. At load and at every subsequent service read, authenticate the caller, compare current policy freshness, verify the exact object/view grant, and deny stale or overbroad entries. A full-repository snapshot must not be distributed to a restricted audience.
4. History and metadata endpoints filter commit identities, parent identities, author/committer fields, messages, signatures, dates, path names, and operation/blob identities under explicit metadata/history rights plus path visibility. Hidden ancestors do not become visible merely because a visible descendant refers to them. A visible projection does not assert that an omitted parent is a root.
5. Search filters and authorizes before ranking, pagination, snippets, facets, and aggregation. Counts, result gaps, ordering, ref names, error details, timing, or cursor contents must not reveal hidden matches. Use a view-filtered index or otherwise isolate/equalize work so hidden matches do not create an observable search signal; if that cannot be established, fail closed for the affected query. Paginate a stable projected snapshot with a cursor bound to view and policy. Denied-versus-missing responses and sizes are normalized; denied object requests never touch the shared object cache. Apply bounded work and rate limits to reduce residual timing inference. Measure and document any residual timing variation; this contract does not claim mathematically constant-time execution.
6. Logs, metrics, traces and crash/error reports must not contain credentials, hidden path bytes, hidden object IDs, raw query text, or unbounded attacker-controlled principal labels. Security audit retains enough protected context to investigate decisions without becoming a side channel to callers.

## Revocation freshness (proposed 30-second bound; owner gate retained)

The proposed bound is: after a policy revocation commits at the authority, no new bytes may be served under the revoked decision more than 30 seconds later. This is a proposed security decision, not an owner-ratified G0 promise. Keep the signoff gate open until the owner accepts the bound, clock/error assumptions, availability tradeoff and measured enforcement plan.

To meet the proposal, every grant and every serving tier's authority-issued policy-freshness lease expires no later than 30 seconds after its authoritative issue/check time. A cache hit cannot extend either expiry. Revocation events invalidate affected grants/projections as soon as received; expiry is the upper bound when an event feed is delayed or unavailable. Grant issuance evaluates the current committed policy version. Before emitting bytes, a tier must establish that its grant and policy-freshness lease are unexpired, audiences match, and no newer policy version/revocation is known. If it cannot establish freshness, the result is deny/unavailable with no stale bytes. More sensitive object grants may require an online authority check on each read.

Clock uncertainty is charged against the bound: the serving tier must stop earlier by its documented maximum clock error, and a tier outside that error budget fails closed. Retries, ranges, streams, resumptions, open handles, snapshots, pre-signed URLs and daemon sessions cannot reset the original grant/freshness expiry. A long-lived session cannot keep a revoked read alive. Already delivered plaintext cannot be remotely erased; local process, sandbox and cache-disk controls limit later access but cannot undo prior delivery.

The 30-second statement is conditional on a documented authority commit point, bounded clocks, and enforceable grant/freshness expiries. Until the owner signs off and implementation evidence demonstrates those assumptions, describe this only as a proposal and do not claim the revocation objective is verified.

## Node socket and local cache trust

1. A node daemon authenticates socket peers using OS peer credentials or an equivalent platform mechanism, then binds a per-session handle to the resolved principal, session, repository, audience, quota and current authorization context. Every request revalidates the handle and scoped object grant. Request fields cannot switch the authenticated principal.
2. Where multiple jobs share one OS user, UID alone is not job isolation. Require a separate unforgeable per-job session credential delivered through a protected channel or an equivalent OS sandbox boundary. PID alone is not a stable identity. Never trust a caller-supplied UID/PID string.
3. Socket directory and endpoint permissions prevent unauthorized connect/replace; peer credentials are verified on the accepted connection. Quotas and request limits are per authenticated tenant/session. Disconnect, expiry or revocation invalidates that session's handles without widening another user's access.
4. The daemon may deduplicate immutable bytes internally. Its raw cache files, keys and storage directory are private to the service account and inaccessible to untrusted jobs. Jobs cannot read cache files directly, ask for another session's memory/disk key, or turn a cache path into an object grant. Cache hits still perform the same principal/repository/view/policy checks as network delivery.

## Bounded failure behavior and evidence boundary

Authorization proof traversal, projection generation, path count, object bytes, stream/range length, search/history work, page size, in-flight requests and per-session concurrency must be bounded under I20. Limits and arithmetic are checked before allocation or partial response. Exceeding a bound returns a typed resource/unavailable failure without raw fallback, partial hidden metadata, or broader retry. Unknown encodings, policies, grant versions and projection algorithms fail closed.

The scenarios below are contract checks, not product tests or implementation evidence. This task's local artifact cannot establish cloud or scale behavior (I16), and its author cannot self-approve or close the task without independent review and integration evidence (I15). Contract satisfaction requires executable tests against the actual authority, each serving tier, node socket, caches and snapshots.

## Limitations and dependencies

- FND-03 owns canonical path parsing and wire representation. This contract defines byte semantics and component-prefix comparison, not transport escaping or canonical changeset encoding.
- FND-04 owns concrete query response schemas; it must represent projected manifests and projected changesets separately from raw content and preserve the distinct projection identity above.
- IAM tasks own executable principal resolution, group/role storage, policy versioning, grant format, freshness checks and socket implementation. This document specifies their security obligations; it does not assert they exist.
- G0 owner/security signoff is required before treating the proposed 30-second revocation bound as accepted. Full acceptance additionally needs independent high-risk review, including two independent Sol reviewers per the task packet, and criterion-level verification on the integrated SHA.
