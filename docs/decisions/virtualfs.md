## 2. Workspace, inode and handle identity

**N01.** A mount binds a workspace UUID, repository, authenticated principal/session, sparse selection version, exact base changeset and authorized effective view/policy. Its namespace is a pinned immutable base plus a private writable overlay. Ref movement never silently changes that base. A requested workspace update is an explicit transaction, not a background ref follower. Object fetching uses the prescribed node → regional → authority route and existing bounded RPCs; native lookup/read/edit MUST NOT shell out to Git or materialize a full native repository.

**N02.** Allocate a nonzero 64-bit inode number and FUSE generation to each logical entry incarnation, including directories. Identity is `(mount epoch, inode number, generation)`, not a path, blob digest or cache address. Two files with identical bytes have distinct inodes. Copy-up, local write/truncate/chmod and rename preserve the entry's identity. Unlink then recreate at the same name creates a new identity; rename-over preserves the source identity and retires the replaced entry. Exhaustion returns a resource error before reuse; no wrap or ABA reuse within an epoch. Persist overlay entry UUIDs in the journal for recovery, but a new mount epoch does not promise the same numeric inode.

**N03.** A successful open creates an opaque nontransferable handle bound to the entry incarnation, access mode, authenticated job/session and authorization provenance. Kernel lookup references and file/directory handles independently pin the entry; FUSE FORGET releases lookup references, RELEASE/RELEASEDIR releases that handle exactly once, neither implies publication or successful sync. Retire only after namespace links, lookup references, handles, snapshots and outstanding I/O references are gone. Cancellation cannot free an object still used by a callback. A stale handle from another epoch/session returns ESTALE or normalized denial; numbers/PIDs are not capabilities.

**N04.** Handles to the same live overlay inode see completed local mutations in their linearization order, with stable identity and updated size/mode. A clean entry replaced by an explicit base update receives a new incarnation; existing handles retain the old immutable bytes/attributes and new opens see the new entry. Unchanged entries retain identity. Directory handles pin an authorized namespace/overlay generation and opaque cookies; enumeration never splices pages from another generation. A new opendir observes later committed changes. Lookup/stat outside that directory handle observes the current committed namespace. Retained generations and pins have finite admission limits. If policy/view changes or freshness expires between readdir pages, stop with normalized denial/staleness (or unavailable for unknown freshness), discard cookies and require a newly authorized opendir; never splice a new view into that handle.

## 3. Consistency, caches and freshness

**N05.** Lookup, stat and initial readdir fetch only needed authorized metadata/pages, with zero blob payload fetches until content is required. Open validates metadata/access; the first read fetches only authorized, integrity-verifiable content on demand. Executable/build access follows the same rule. Never invent zeros for unavailable remote bytes, substitute another revision, return a raw internal tree page to a restricted reader or use a digest as authority. Derived tree page IDs are not canonical tree TIDs; canonical v1 has blob and changeset kinds only.

**N06.** Immutable cache bytes are keyed and verified by typed identity; mutable decisions, dentries, attributes, negative entries and projections are keyed by principal/session, repository, base/view, policy and namespace generation as applicable. Snapshot seeds populate the object cache, never the workspace/dirty overlay. Verify manifest integrity, version, declared scope, timestamps and digests before atomic seed activation; discard invalid/incomplete seeds safely. Every subsequent delivery reauthorizes. Projection bindings include source, effective view, policy, exact tagged selection, algorithm/version and visible content; expose only authorized opaque aliases/cursors, not raw roots, hidden identities, counts or boundaries. Policy/view changes invalidate continuations even if visible bytes happen to match.

**N07.** ADR-007 is an approved **maximum 30-second revocation design target after authority revocation commit**, with runtime enforcement UNVERIFIED. Every new byte or metadata delivery, including a hot hit, range, resumed stream, snapshot, directory handle and local daemon handle, requires current authorization, a live exact grant where applicable and proven policy freshness. Known revocation stops delivery immediately. Expiry is exclusive: `now >= expiry` denies. Grant/freshness lifetimes are at most 30 seconds from their authority issue/check; bounded clock error is subtracted from the usable deadline. Unknown freshness or unbounded clock error fails closed, with no stale bytes. Retries, ranges, streams, resumptions, open handles, snapshots and daemon sessions never reset original grant/freshness expiry, session expiry, quota or an in-flight call's deadline. Renewal supplies credentials for a later explicitly authorized call only; an in-flight call cannot adopt them or extend its original serving deadline. Changed policy/view requires explicit new authorization under grants-v1, not transparent continuation.

**N08.** Initial supported security profile MUST disable kernel content caching with direct I/O, disable writeback cache, and use zero positive/negative dentry and attribute TTLs. No mmap (including executable mappings), splice/cache shortcut or inherited descriptor may bypass checks; unsupported paths fail explicitly before data exposure. Userspace metadata/snapshot caches still recheck N07. Permission changes require invalidation of retained handles/projections and any kernel state before further delivery; failure fences the session/mount. Future kernel caching/mmap support needs a separately reviewed enforcement proof, including mappings and credential changes. Already delivered plaintext, including application buffers, cannot be recalled; that fact does not permit new cached delivery after expiry.

The mmap restriction is a visible compatibility blocker for ordinary compilers/loaders/build tools needing mappings. Full R29 build-tool acceptance remains outstanding until an enforceable profile passes those real workloads; this document does not redefine that requirement away. A remote outage permits only already authorized cached reads within proven freshness; expiry or missing bytes returns explicit failure. Cache-tier failure MUST NOT trigger direct authority bypass or an unbounded miss storm.

## 4. Writable overlay and concurrent updates

**N09.** The overlay supports create, write, truncate, unlink, mkdir/rmdir, rename and regular/executable mode changes; immutable base objects are never modified. New entries/tombstones and byte extents belong to one workspace/session. Other workspaces, sessions and published readers cannot see them before an explicit authorized publication. A second authorized process in the same isolated job/workspace sees completed local changes immediately; there is no implicit cross-user sharing. Empty directories may exist locally, but canonical v1 cannot publish them: report an explicit unsupported-input blocker without dropping them or claiming lossless publication.

**N10.** Before the first possible content/namespace mutation, durably save Dirty/Uncertain metadata and an intent identifying operation, inode UUIDs, old/new parent generations and affected content extents. Assign a durable local operation ID `(workspace UUID, mount epoch, FUSE request unique ID)` before mutation, binding session, opcode, inode/generation, offset/length and content digest or source/destination parent/name generations. Retain exact intent, accepted prefix and terminal result: identical-ID/tuple retry returns that result without repeating effects; changed tuple conflicts. Expose status only through authenticated owner recovery, never treat a new syscall ID as the same retry. Retention lasts through original request deadline, completion/cancellation and a durable recovery checkpoint; finite record/byte caps block admission rather than discard unresolved records. After collection, no replay guarantee is claimed; unresolved outcome requires explicit recovery, not a fresh append. Journal records are bounded, checksummed and versioned. A completed ordinary write may be volatile until fsync, but its dirty/recovery marker is durable first. Copy-up is lazy and range-based; obtain only needed old ranges before overwrite, retain untouched remote extents with exact base identities and never hydrate an entire large file merely to change a small range. Truncate growth defines zero-filled local holes; truncate shrink discards the suffix in the overlay only. A lost remote extent is an error, not a zero-filled hole.

**N11.** Each admitted mutation has one namespace/content linearization point. Serialize conflicting operations per inode/affected directory transaction; use ordered acquisition or bounded optimistic generation checks, never a repository-wide commit lock or global ingestion sequencer. A successful write exposes its accepted range coherently; concurrent overlapping writes use the last linearized accepted bytes. Nonoverlapping writes survive together. O_APPEND reserves EOF and installs accepted bytes atomically per inode. Short writes return exactly the accepted byte count; errors never imply that an unreported suffix was written. Concurrent truncate/write order determines size/content; reads see one committed extent map for their request. No whole-file snapshot across separate read calls is promised for a file being edited.

**N12.** An explicit base/sparse update stages a new immutable view, detects dirty entries and all intersecting ancestor/descendant rename/delete/mode conflicts, then atomically swaps the namespace/base manifest only after required local durability. A conflict returns a bounded visible conflict result (EBUSY at the filesystem adapter); preserve the old base and every dirty byte. Never silently overwrite dirty content or rebase a handle. Disjoint updates may proceed using generation validation; a raced generation retries within a finite budget or conflicts. Watcher events are hints; overflow, cancellation or uncertainty marks Uncertain and requires bounded reconciliation, never automatic Clean or a full unbounded scan.

## 5. Rename, removal and authorization

**N13.** Rename within one workspace is atomic for observers: either both source removal and destination installation/replacement occur or neither does. Across directories, validate source removal, destination creation, ancestor traversal and replacement rights independently under the same current policy, before mutation; explicit deny wins. Directory moves must authorize the affected descendant paths at both locations, including existing deny rules, within a finite traversal/proof budget. If proof cannot be completed, fail closed without a partial move or hidden-name diagnostic. Revalidate policy and parent/inode generations at commit. Ordered per-directory metadata coordination is allowed, not repository-wide serialization.

**N14.** Reject cross-workspace/mount/repository rename with EXDEV, directory-into-descendant with EINVAL, incompatible file/directory replacement with EISDIR/ENOTDIR, and replacement/removal of a nonempty directory with ENOTEMPTY, only where those facts may be disclosed. RENAME_NOREPLACE returns EEXIST for a visible destination. Unsupported exchange/whiteout flags return EOPNOTSUPP without mutation. Atomic local rename is not a canonical rename opcode: publication computes explicit sorted DELETE/SET leaf operations against parent zero and validates the complete final prefix-free map. Directory deletion requires all removed tracked leaves explicitly; never infer recursive canonical DELETE.

**N15.** Rename does not retarget open source handles to the replaced destination inode; handles to the replaced inode retain its old bytes. Unlink removes namespace visibility immediately while an open handle pins its entry/content. New lookup gets normalized missing; unlink/recreate cannot redirect an old descriptor. An open orphan may read/write its private inode while still authorized, but does not implicitly reappear or become publishable under the deleted name. Its data is retained until final references and recovery obligations end; dirty orphan loss requires explicit user discard, not cache eviction.

**N16.** Open is not permanent authority. Each read/write/getattr/readdir/fsync revalidates the bound job/session, current policy and operation rights. Remote immutable extents require an exact blob grant with reachability proof anchored to their original immutable `(revision, path)` even after local rename/unlink. Workspace-owned new/dirty extents instead require authenticated workspace/session ownership and current visible-path rights; they are not ObjectGrants and require separate upload authorization later. After rename, every subsequent operation additionally requires current rights at the new visible location. An unlinked/replaced handle keeps its protected original authorization provenance and checks current policy at its last authorized path; it never gains replacement rights. For remote extents, stale/unreachable/unprovable reachability means deny further operations rather than minting an orphan grant or borrowing another path/session's grant. Local dirty orphans require current workspace/path rights, remain private and cannot be published under a deleted name. Revocation fences even unlinked handles and dirty data; preserve recoverable private bytes but expose them only through a newly authorized recovery flow. Closing/final cleanup can release resources without returning protected bytes or granting publication. N07 applies regardless of namespace lifetime.

## 6. Flush, fsync, durable sync and immutable publication

**N17.** FUSE FLUSH may occur multiple times for duplicated descriptors and is not a final close. It waits for that handle's admitted writes and reports retained write errors; it does **not** promise stable-storage durability, upload, changeset publication or a ref update. RELEASE is resource cleanup; an application cannot rely on its error as a successful close-time sync. Retain asynchronous errors by inode/handle until explicitly acknowledged through a reportable operation; never erase them because another descriptor closed.

**N18.** File fsync waits through the captured inode write sequence, persists data extents/size/mode and recovery metadata, syncs containing journal/storage directories required for replay, then reports success only when the declared local storage backend guarantees those bytes survive process restart. fdatasync may omit unrelated timestamps, never size or replay metadata needed to retrieve bytes. Directory fsync durably records completed creates/deletes/renames; cross-directory rename requires both parents and the shared intent durable. A racing later write remains dirty and outside the captured fsync barrier. Any write/fsync/directory-sync/close failure returns an error and preserves Dirty/Uncertain; no silent durable acknowledgement. Physical power-loss durability requires real backend evidence and is presently unverified.

**N19.** Explicit workspace durable sync snapshots the current overlay sequence, fsyncs its referenced data and namespace journal, persists exact base/selection plus recoverable dirty state, and records a durable local checkpoint. Later writes remain a new dirty sequence. Local sync never implies authority storage or immutable publication. Optional explicit upload uses authority-only BeginUpload/UploadChunks/FinishUpload with current scoped UPLOAD grants, exact intent, bounded RAW chunks and idempotency; READ grants cannot upload and upload grants confer no read/publication rights. FinishUpload confirms a durable verified object only, not a published changeset or ref movement.

**N20.** Explicit publication freezes one overlay sequence, validates the full simultaneous canonical delta and every current path/metadata/parent permission, durably uploads/verifies all required blobs, and calls the existing changeset publication operation with a retained idempotency key. Acknowledgement requires durable immutable changeset, durable referenced blobs, valid published parents and retained identity/result. No mutable overlay state, partial upload or fsync is a published revision. Publication is detached and requires no repository-wide lock; a separately requested ref update compares **both expected target and generation**. Ref conflict leaves the published immutable changeset intact and the workspace recoverable; it cannot roll it back or rewrite history. Only reconciled included changes may become Clean; later writes, unresolved orphans/unsupported inputs and ambiguous results remain dirty. No implicit publication on close, unmount or retry.

## 7. Crash, cancellation, retry and partial failures

**N21.** Recovery validates exact workspace/session ownership, versions, checksums, extents and operation generations before serving. Before mutation, failed intent/Dirty persistence means no mutation. After an acknowledged volatile write but before fsync, bytes may be lost on crash; durable intent must force Uncertain, never falsely Clean. After successful fsync/checkpoint, restart must recover the durable sequence or return a visible corruption/storage-loss error, not fall back to an older clean workspace. Interrupted rename replays/rolls back the journaled transaction as one unit, not two independently visible directory edits. A torn/corrupt journal is quarantined for explicit recovery; never delete it and guess success. Process crash is not proof of physical power-loss safety.

**N22.** Daemon death fails pending I/O explicitly; restart creates a new mount/session epoch and stale descriptors are not silently reattached. Private overlay/journal persists, while immutable cache entries may be reverified/rebuilt. Retry is bounded by original deadline, attempt count and work/byte budgets. Before the linearization point, cancellation returns EINTR with no mutation; after it, record/query the committed result and never undo an acknowledged effect. Partial writes preserve their accepted count and durable intent. FUSE INTERRUPT alone is not evidence that the underlying operation did not commit. A lost response is ambiguous until the retained operation record resolves it; never blindly replay append/rename as a fresh request.

**N23.** Upload/publication timeouts retain exact intent, source sequence, key and any operation identity. Use the same-key status/retry path within retained idempotency lifetime; changed intent conflicts. An unknown authority outcome is UNAVAILABLE/uncertain, not success, rollback or permission to create a second logical effect. Query existing GetOperationStatus where applicable; if status cannot be established, stop and retain dirty state. No automatic new key after expiry; require an explicit newly authorized decision. Partial uploads are private, bounded staging; verified objects become usable only after complete integrity/durability checks, unreachable objects may later be collected, and no partial publication/root becomes visible.

| Failure class | Required visible outcome / retention |
|---|---|
| Hidden, missing, foreign or unauthorized object/path/handle | Same normalized ENOENT/public NOT_AVAILABLE shape before cache probing; no hidden detail, counts, IDs or timing-dependent fallback. EACCES is reserved for disclosable local access failures. |
| Unknown freshness, authority outage or deadline | EAGAIN / ETIMEDOUT with protected typed UNAVAILABLE / DEADLINE_EXCEEDED context; no stale bytes, fabricated zeros, broader retry or topology bypass. |
| Local storage full, quota, queue/FD/pin exhaustion | ENOSPC / EDQUOT / EAGAIN or EMFILE as appropriate, before unadmitted work; preserve all accepted dirty data and report any accepted short-write prefix. |
| Integrity failure, unsupported operation/name, conflict | EIO, EOPNOTSUPP/ENAMETOOLONG, or EBUSY respectively for disclosable facts; retain quarantine/recovery evidence, do not silently normalize/skip. |

## 8. Finite resources and path containment

**N24.** Before mount admission, configure positive finite hard limits for resident metadata/content bytes, decoded/encoded buffers, total immutable disk bytes, dirty disk bytes, journal records/bytes, open handles/FDs, inode generations, retained directory snapshots, pinned bytes, proof traversal/depth/CPU, in-flight fetches, queued requests and per-job work. Reject absent/overflowing limits. Validate sizes/counts/offset arithmetic before allocation. Stream large files in bounded ranges/chunks, propagate cancellation, use fair per-session admission and backpressure; queue saturation returns promptly, never an unbounded wait. Pin exhaustion rejects a new open/opendir/update instead of allocating indefinitely. Dirty data is separate from evictable cache; pressure cannot evict it or send work past a failed tier. Concrete tuned VFS limits and measured envelopes remain implementation/qualification gates, not claims from this document.

**N25.** Enforce tighter applicable canonical/grants limits without changing their maxima: canonical paths up to 65,535 bytes/1,024 components, blobs up to 2^40 streamed bytes, changeset payload at most 64 MiB/1,000,000 operations; grants-v1 caps and one active delivery per stream remain in force. Finite resource refusal does not downgrade required large/wide/deep cases: retain an explicit blocked input/workload ledger. Small edits must scale with changed paths/structure and bounded history work, not repository size. No full mirror, pack negotiation or unbounded reconciliation fallback.

**N26.** Paths remain exact canonical raw bytes: `/` alone separates components; reject NUL, empty components, absolute repository paths and exact `.`/`..`; no case folding, Unicode normalization, percent decoding or backslash translation. Linux component/path syscall constraints can be stricter than canonical limits: preflight and report unrepresentable names/collisions as explicit blockers, never rename/drop them. Kernel navigation at the mount root cannot become a userspace backing-store path. All backing metadata/overlay I/O uses held root directory descriptors, no-follow component resolution and checked ownership/types; revalidate against symlink/rename races. Never concatenate untrusted names into an absolute host path.

**N27.** Symlink blobs retain their exact canonical bytes; readlink is bounded and requires the existing `read` right on the symlink entry, not a new permission action; following it additionally requires ancestor `traverse` and the requested target operation rights. Admission rejects absolute, NUL-containing, escaping or otherwise unrepresentable link targets in the safe virtual profile. Relative resolution must stay beneath the virtual root, reject loops/depth overflow and authorize every traversed target; a symlink never elevates rights. Linux VFS may resolve a returned link in the caller's namespace, so the mount alone cannot contain hostile link/`..` traversal or descriptor passing: require a job filesystem sandbox/root boundary that denies outside access, and fail admission if that boundary cannot be established. Backing writes never follow repository symlinks. Unsupported safe exposure remains a blocker, not permission to rewrite stored link bytes. Devices, FIFOs, sockets, hard links, setuid/setgid changes and unsupported xattrs return EOPNOTSUPP; only canonical regular/executable/symlink modes may enter publication.

## 9. Local daemon and multi-user isolation

**N28.** Authenticate Unix socket peers with Linux SO_PEERCRED or equivalent verified OS credentials, then authenticate the protected per-job principal/session binding. Caller UID/PID text and PID reuse are never identity; SO_PEERCRED's connection identity alone does not authenticate a descriptor's later recipient. Multiple jobs sharing a UID require an unforgeable protected job credential and/or equivalent OS sandbox boundary that prevents credential theft. If that isolation is unavailable, fail closed. Per-request credentials, mount/job boundary and descriptor-transfer controls must prevent another job from borrowing an authorized handle; an inherited fd never changes its bound principal into the daemon's service identity.

**N29.** Use private owned socket directories/endpoints and private service-account cache files/keys; untrusted jobs never directly read raw deduplicated cache pages. Overlay/journal storage is private to its workspace owner and protected from other jobs including same-UID jobs by the required sandbox. Every request binds principal/session, repository, audience, view/policy, quota and exact object/path rights before protected lookup. Authenticate/check current grants even on hits; disconnect, expiry or revocation invalidates session handles. FUSE request UID/GID/PID fields, default_permissions and local mode bits supplement but never replace repository authorization. Default mount is one isolated job; allow_other/allow_root and cross-user mount sharing are unsupported until independently proven per-request isolation exists. Different sessions cannot share a mutable overlay or permission decision because bytes match.

## 10. Linux prerequisites, lifecycle and outstanding gate

**P01.** Real acceptance needs a Linux kernel with FUSE filesystem support (`CONFIG_FUSE_FS`, built in or an already available module), accessible `/dev/fuse`, a usable FUSE protocol connection and compatible userspace low-level FUSE3 library/server plus the distribution's `fusermount3` helper for unprivileged mounting. Freeze actual kernel release/config, architecture, FUSE protocol/library/helper versions and negotiated capabilities in future evidence; this design selects no untested minimum kernel/library version. The server must implement the callbacks and direct-I/O/invalidation behavior required above. Merely finding a device/library or compiling callbacks is not mount proof.

**P02.** Use an ordinary authorized test user, a private empty owned mountpoint, searchable parent directories, writable private durable overlay/journal storage, private socket/cache paths and sufficient admitted FD/disk limits. `/dev/fuse` access, OS security policy (including LSM rules) and the helper must permit the operation. Typical unprivileged mounting relies on an administrator-installed privileged `fusermount3`; direct privileged mounting requires appropriate CAP_SYS_ADMIN in the relevant namespace. Neither capability, device, module, helper privilege, mount namespace nor policy may be added by this lease. A container device mapping or a Docker engine does not establish these permissions. Failure leaves the real gate blocked; no privileged fallback. Keep nodev/nosuid and omit allow_other/allow_root; do not enable user_allow_other to bypass isolation. Execution permissions must match the separately tested executable profile.

**P03.** A future authorized runner must verify prerequisites and an uncontaminated mountpoint, recover the owned journal, authenticate/admit the session, establish the mount and demonstrate ordinary kernel-mediated I/O from an independent process. Record mount identity, mount table, server PID/epoch, credentials/namespace, actual options/capabilities and fetch counters. Normal shutdown stops new admission, drains bounded I/O, explicitly fsyncs/checkpoints dirty state, reports all errors, closes handles and requests normal owner unmount via the installed helper. Busy unmount returns EBUSY; timeout is a recorded failure, not success. A forced/lazy detach is an explicit separately authorized recovery action, never proof of a clean unmount.

**P04.** On failed setup, interrupted tests or daemon death, fence grants/session and cancel bounded outstanding work; preserve logs, dirty overlay and journal. The authorized runner must distinguish never-mounted, mounted, detached and still-busy states by exact owned mount identity; clean up only its own connection/mountpoint after references release. Never recursively delete through a live/stale mount or remove another mount's directory. If cleanup cannot finish without privilege expansion, stop with residual mount/process identities and a host recovery handoff. Do not discard dirty bytes to make teardown pass. Restart/recovery and subsequent normal mount/unmount need separate recorded outcomes.

**P05.** The current host is Darwin/arm64; no verified Linux FUSE mount capability is available to this attempt. Linux real-mount runtime acceptance is **BLOCKED / NOT EXECUTED**, not passed or waived. No Docker/container, FUSE/mount/unmount command, privilege expansion, download, cloud run or deployment is authorized here. macOS (including macFUSE), Windows, BSD, network filesystems and other kernel/architecture combinations are unsupported/unverified for this VFS contract; CLI-01's Darwin metadata result provides no portability proof. Required portability work remains explicit scope, not an inferred promise.
