## Fidelity classes and fail-closed rules

Classes describe a possible mapping under the pinned contract, **never an implemented support claim**. Use the most restrictive class for the row's stated scope:

- **E (exact payload)**: the specified byte payload/path/mode can be identical in the target within v1 limits. Native object identity still differs; original framing/OID stays provenance.
- **S (declared semantics)**: specified logical fields/graph or leaf state can map exactly, but native framing, lexical spelling, container structure or ancillary semantics cannot be reproduced from canonical data alone.
- **P (provenance only)**: raw source evidence can be retained, but the source feature has no agreed operational target mapping. Provenance retention is not functional fidelity.
- **U (unrepresentable)**: the required native meaning is absent from v1 or exceeds its bounds; durable evidence plus a migration blocker is mandatory. Storing opaque bytes in a blob does not create the missing meaning.
- **X (invalid or incomplete)**: validity, completeness or authority cannot be established; no successful mapping/publication may be claimed.

**HOLD** means no migration acceptance until an implemented mapping and criterion-specific parity evidence exist, even for E/S rows. **BLOCK+MANIFEST** means stop acceptance for the affected migration scope and preserve a durable, protected unsupported-input manifest before acknowledging inventory. It is not success, not “skip,” and not an exclusion. **QUARANTINE+MANIFEST** retains bounded, untrusted evidence without serving or publishing a verified target; the blocker remains. If manifest persistence fails, fail the operation; do not acknowledge durable capture. Malformed input and denied access never trigger fetching or broader retries.

Every manifest entry must bind matrix row ID, source repository identity, inventory snapshot/watermark, source object type, explicit hash algorithm and full OID, raw evidence blob identity/digest (or an explicit missing/unreadable reason), byte-exact ref/path and mode where relevant, evidence completeness/verification state, reason code, target TID if one exists, policy/contract version, accountable owner/action and unresolved status. Encode bytes reversibly (for example hex/base64), never lossy display text. [P-CANON] specifies an append-only, versioned source/native mapping around a **native changeset TID**, binding repository, source system/type/algorithm/OID, exact raw-source blob TID and signature evidence; retries cannot retarget that binding. It does **not** freeze a general Git blob/tree/tag-to-canonical-object ledger. Any general ledger described in FMT/OBJ rows is future policy only and remains a migration acceptance blocker until the canonical contract owner and migration lead ratify its schema/version, raw-object identity boundaries, authorization, durability and retry/conflict rules. A raw-source blob is provenance, not a canonical tree/tag representation. Preserve logical Git header/type/length/content needed to rehash, plus any separately required storage evidence. Compression and pack layout are not canonical identity.

Manifest/raw-object/mapping access is protected by [P-SEC]/[P-GRANT], including metadata/history, snapshots, caches and multi-user daemons. A digest never grants access. Denied/inaccessible inputs remain protected blockers without leaking their paths, IDs, counts or presence to unauthorized callers. No cache-tier bypass is authorized. A source repository's config, attributes, hooks and embedded URLs are untrusted data; this policy executes none.

Owners named below are **accountable roles needing director assignment**, not inferred approvals: migration lead (mapping/parity and manifest design); canonical contract owner (v1 amendments/vectors); security owner (trust, disclosure, auth and network policy); source owner (inventory/completeness and source freeze); consumer/checkout owner (host materialization and external consumers). An exclusion would require an explicit, pinned owner decision with precise scope and retained blocker history. None is currently available. All rows map to C1 (inventory/fidelity) and C2 (unsupported handling).

## Git LFS

LFS and Git hash domains are separate. A Git blob containing a pointer has its own Git OID. The pointer's `oid sha256:...` describes external payload content, while a canonical blob TID hashes its canonical frame. None can be substituted for another. Keeping pointer bytes does not deliver external file content.
